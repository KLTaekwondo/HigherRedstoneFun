## 1. 结论速览

1. **Slimefun4 是一个「无模组模组包」类型的 Bukkit/Paper 插件**，用一本图鉴书（Slimefun Guide）承载 500+ 新物品、22 个分类、258 个研究、16 台多方块机器与一整套"焦耳(J)"电力网络。官方 README 自述 "over 500 new items and recipes"（[README](https://github.com/Slimefun/Slimefun4/blob/master/README.md)）。
2. **本体由 2013 年 mrCookieSlime 个人项目演化为社区维护项目**；作者 2016 年退休改名 TheBusyBiscuit，此后长期由社区贡献者维护（[Slimefun 的故事](https://slimefun-wiki.guizhanss.cn/Slimefun-in-a-nutshell/)）。
3. **上游事实已停止开发**：`experimental` 分支最后一次**功能性**提交为 **2025-03-09**（`Support 1.21-1.21.2` / `Update to 1.21`），最后一次提交为 **2025-05-01**（renovate 机器人配置），最新 release 停在 **RC-37**。第三方服主公告（2025-10-15）明确写道开发者"announced that active development has officially ended after more than twelve years"。**GitHub 仓库未被 archive，官方公告原文 URL 未核实**，但社区已按"已停更"行动，涌现 SlimefunLegacy / Slimefun4Core / Slimefun-United 等多个分支。
4. **中文生态不是"翻译层"而是"续命层"**：`SlimefunGuguProject`（鬼斩 ybw0014 等）与 `StarWishsama/Slimefun4` 汉化分支持续构建，且多款附属**汉化版比原版上游更活跃**（如 Gastronomicon、Cultivation）。
5. **研究系统是纯 XP 等级门槛，且总量极大**：源码核实 **258 个研究、ID 范围 0–281、单个解锁成本 1–60 级、全部解锁合计 5431 XP 等级**，配合 39 级"研究等级"称谓。这是玩家抱怨"太肝"的核心来源。
6. **能源网络的心智负担来自三条硬规则**：① 必须存在**能源调节器**，否则不导电；② 网络按**每 10 game tick（=0.5 秒）**整体重算一次；③ 电容/连接器需在**直线距离约 6–7 格内**才能连通。连两个调节器会直接报 "Multiple Energy Regulators connected"。
7. **发电机产能跨度为 4 J/s → 1024 J/s**，与用电机的 2–180 J/s 消耗相比**中期就会出现严重产能过剩**（一台核反应堆 500 J/s 可带满多数产线），这也是玩家反馈"后期电网无意义"的原因（源码核实，见第 6 章）。
8. **货运（Cargo）系统是最受诟病的性能热点**：官方优化指南用整整一节讲货运限流，并承认"货运网络是已知的影响性能较大的部分"（[服务器优化指南](https://slimefun-wiki.guizhanss.cn/Server-Optimizations/)）。
9. **附属插件生态规模：官方英文 Wiki 收录 87 个条目**（17 官方 + 65 社区 + 5 第三方），中文 Wiki 收录 **182 个**（含大量国产附属）。但**绝大多数已 1–3 年无功能更新** —— 本次抽样 38 款中仅约 4 款半年内有提交。
10. **「基因 / 育种」方向是真实空白**：本体只有加速器（作物/动物/树木）而无遗传机制；生态中仅 `GeneticChickengineering-Reborn`（已归档）、`GeneticManipulation`（RC-27 时代）、`Cultivation`（交叉培育，最接近）三款沾边。这是一个**可差异化切入的生态位**。
11. **本体的性能痛点有一条清晰的"未修复因果链"**：官方 ADR-0001（2023-11）自认 BlockStorage 用 YAML 存数据是错误设计（"good for a config format but **not good for a data store**"，会产生 "files that can get corrupted"），而其改造计划 **Phase 2–6 全部 Not started**；结合 2025 年停更可知，**这些问题是有意被搁置而非无人发现**。这为本项目提供了明确的"已知坑位清单"。

## 2. 粘液科技是什么

### 2.1 一句话定义

Slimefun 是一个**服务端插件**，目标是在**不安装任何 Mod** 的前提下，把原版 Minecraft 服务器变成 FTB 风格的"模组包"体验：新增物品、多方块机器、电力网络、物品物流、魔法祭坛、机器人、GPS 传送等系统。

官方 `plugin.yml` 的 description 原文：

> "Slimefun basically turns your entire Server into a FTB modpack without installing a single mod"

（来源：[`src/main/resources/plugin.yml`](https://github.com/Slimefun/Slimefun4/blob/master/src/main/resources/plugin.yml)，源码核实）

### 2.2 版本史（Slimefun 1 → 4）

| 代际 | 时间 | 关键内容 | 来源 |
|---|---|---|---|
| Slimefun 1 | **2013 年** | mrCookieSlime 开发的 Bukkit 插件，最初版本只提供少量新物品 | [Slimefun 的故事](https://slimefun-wiki.guizhanss.cn/Slimefun-in-a-nutshell/) |
| Slimefun 2 | **2013 年末** | **引入研究系统**、一本正式的使用指南书、装备、武器 | 同上 |
| Slimefun 3 | **2014 年** | 转向科技主题：矿机、太阳能板、电机、背包；被大量生存/小镇/空岛服采用 | 同上 |
| Slimefun 4 | **2015 年底 Beta**（限 "Cookie's Realm" 服务器）<br>**2016 年 4 月公开发布** | **物品运输、能源网络、核反应堆、GPS 与卫星系统、可编程开采/耕作机器人**；同时在 GitHub 开源 | 同上 |

- **Walshy（WalshyDev）**：2019 年起与 TheBusyBiscuit 一起改善代码质量与性能。
- **2019 年初**创建官方 Discord；**2020 年 1 月**破 1000 人，**2020 年 6 月**破 2000 人，**2021 年初**超 4500 人。
- **2020 年 4 月、2021 年 4 月**举办两届 Addon Jam（附属插件开发竞赛），产出了本次调研中的多款知名附属。

## 3. 核心玩法机制

### 3.1 图鉴系统（Slimefun Guide）

玩家进入服务器会收到一本**粘液科技指南书**（`guide.receive-on-first-join: true`），它是所有内容的入口：分类浏览、配方查看、研究解锁、搜索。

相关配置（源码核实，`config.yml`）：

```yaml
guide:
  show-vanilla-recipes: true      # 是否显示原版配方
  receive-on-first-join: true     # 首次进服自动发书
  show-hidden-item-groups-in-search: false
```

- 对应命令：`/sf guide`（给自己发书）、`/sf open_guide`（不开书直接打开，默认仅 OP）、`/sf search <关键词>`。
- 权限：`slimefun.command.guide`（默认所有人）、`slimefun.command.search`（默认所有人）、`slimefun.command.open_guide`（默认 OP）。

### 3.2 研究系统（Research）

**这是 Slimefun 的科技树门槛机制。**

#### 机制（源码核实）

- 核心类：`io.github.thebusybiscuit.slimefun4.api.researches.Research`
- 注册器：`implementation/setup/ResearchSetup.java`
- 一个 `Research` 绑定 **1 个或多个 SlimefunItem**，并带有一个 **`cost`（以玩家 XP 等级计）**。
- 构造函数签名：`Research(NamespacedKey key, int id, String defaultName, int defaultCost)`
- 校验逻辑：`setCost(int cost)` 在 `cost < 0` 时抛 `IllegalArgumentException("Research cost must be zero or greater!")`
- 玩家侧：`PlayerProfile.hasUnlocked(research)` 判定是否已解锁；`Research.canUnlock(player)` 判定是否满足条件；解锁时触发 `ResearchUnlockEvent`。
- **解锁入口是图鉴书本身**：`Research#unlockFromGuide(guide, player, profile, sfItem, itemGroup, page)` —— 即在图鉴里点开未解锁物品，点击解锁按钮花费 XP 等级。**原版 Slimefun4 中不存在"研究台"方块**（源码核实：全仓库搜索 `RESEARCH_BENCH` / `ResearchBench` 无任何命中）。

> **⚠️ 对任务书的一处订正**：任务描述中的"研究台"以及"蓝图"概念，**在 Slimefun4 本体中并不存在**。本体的研究解锁是**纯 UI 操作 + XP 等级消耗**，没有实体方块，也没有"蓝图"物品。相关概念可能来自某些附属插件或玩家的俗称，**标注为「未核实」**。

### 3.4 能源与电力系统（EnergyNet）

**这是 Slimefun 最复杂、也最被诟病的系统。**

#### 3.4.1 基本概念

| 概念 | 说明 | 来源 |
|---|---|---|
| 单位 | **焦耳（J）** | [能源与电力](https://slimefun-wiki.guizhanss.cn/Electric-Machines/) |

| 能源连接器（Energy Connector） | 扩展能源网络范围 | 同上 |
| 电容（Capacitor） | 存储能量 + 扩展网络范围 | 同上 |
| 万用表（Multimeter） | 查看精确电量数值 | 同上 |

#### 3.4.2 网络组成规则（源码核实）

源码 `core/networks/energy/EnergyNet.java`：

```java
public class EnergyNet extends Network implements HologramOwner {
    private static final int RANGE = 6;
```

`classifyLocation()` 把方块分为三类：
- `CONNECTOR`（连接器 / 电容）→ 网络的**通路**
- `TERMINUS`（`CONSUMER` 用电机 / `GENERATOR` 发电机）→ 网络的**端点**
- `REGULATOR`（能源调节器）→ 网络的**根**

`EnergyNetComponentType` 枚举只有 4 个值：`GENERATOR, CAPACITOR, CONSUMER, CONNECTOR`。

**一个网络只能有一个能源调节器**。若检测到多个：

```java
if (!regulator.equals(b.getLocation())) {
    updateHologram(b, "&4Multiple Energy Regulators connected");
    ...
    return;
}
```

没有连接任何节点时显示 `"&4No Energy Network found"`。

#### 3.4.3 网络 Tick 调度（源码核实）

调度顺序（`EnergyNet#tick`）：

1. `tickAllGenerators()` —— 遍历所有发电机，累加 `provider.getGeneratedOutput()`。
2. `tickAllCapacitors()` —— 累加所有电容当前电量。
3. `supply = generators + capacitors`；`remainingEnergy = supply`。
4. `tickAllConsumers()` —— 逐个用电机，计算 `availableSpace = capacity - charge` 累加为 `demand`；把 `remainingEnergy` 塞进未满的用电机。
5. `storeRemainingEnergy(remainingEnergy)` —— 剩余电量按顺序充入电容、再充入发电机的内部缓存。
6. `updateHologram(b, supply, demand)` —— 全息显示净盈（`+N J`）或净亏（`-N J`）。

**关键设计事实**：
- **电量每 tick 被完全重新计算**，不是"累积余额"模型。
- 机器自身缓存（非电容）**在本 tick 结束时若未被使用并不会跨 tick 保留** —— 官方 Wiki 明确写道："某些机器可以储存能源。但它们不像电容，如果储存的电能在达到峰值前没有被使用，它就会被立即重置。"
- 数值使用 `NumberUtils.flowSafeAddition()` 做**整型溢出保护** —— 说明能量值是 `int`，存在上限约束。
- 发电机有 `willExplode()` 判定：过热的反应堆会被替换为**岩浆方块并原地爆炸**。

**Tick 频率**：由 `config.yml` 的 `URID.custom-ticker-delay` 控制，**默认 10**（即每 10 game tick = **0.5 秒**执行一次）。`implementation/tasks/TickerTask.java` 中：

```java
this.tickRate = Slimefun.getCfg().getInt("URID.custom-ticker-delay");
scheduler.runTaskTimerAsynchronously(plugin, this, 100L, tickRate);
```

> **⚠️ 单位陷阱**：游戏内 tooltip 显示的发电量是 `getEnergyProduction() * 2 + " J/s"`（源码 `AbstractEnergyProvider`）。也就是说源码里的 `getEnergyProduction()` 是**每网络 tick（0.5 s）的值**，而展示值与官方 Wiki 表格用的是**每秒值**（×2）。官方 Wiki 的[反应堆](https://slimefun-wiki.guizhanss.cn/Reactors/)表格把单位写成 "J/t" 却填的是 ×2 后的值，**这个单位标注是错的**，阅读时需注意。

**分类设计机制（源码核实）**：

- **`LockedItemGroup`**：需要先解锁父分类才可见。`electricity` / `androids` / `cargo` / `gps` **四个组都以 `basicMachines` 为父**（`new LockedItemGroup(..., basicMachines.getKey())`）——这是"科技树门控"的核心实现。
- **`SeasonalItemGroup`**：绑定月份（`Month.DECEMBER` / `FEBRUARY` / `APRIL` / `OCTOBER`），**只在特定月份显示**。这是 Slimefun 很独特的设计——内容会"过季消失"。
- 语言文件 `languages/en/categories.yml` 有 **24 个 key**（22 个组 + `talismans` + `ender_talismans` 两个护身符子分类 key）。

**分类数结论：22 个图鉴分类（17 常规 + 5 季节性），外加 2 个护身符子分类 key，语言文件共 24 条。**

- **SC → RSC 是明确的继任路线**：存在 `SC-to-RSC` 配置转换工具。
- **ybw0014（鬼斩）是中文生态枢纽**：同时主导 InfinityExpansion2、FastMachines、GeneticChickengineering-Reborn、VillagerTrade、SlimefunTranslation、GuizhanCraft、Guizhan Builds 构建站与中文附属 Wiki。

### 6.4 能源网络连接规则与常见痛点

#### 连接规则（源码 + Wiki 交叉核实）

1. **必须有且只有一个能源调节器**。多个 → 全息显示 "Multiple Energy Regulators connected" 并**停止网络 tick**。
2. **电容和能源连接器充当"导线"**，同时也可以当"电池"。
3. **连通距离**：源码 `EnergyNet.RANGE = 6`；官方 Wiki 表述为 **7 格以内（直线，不可对角）**。**存在 1 格差异（未核实）**。
4. **用电机与发电机是"终点"**，不会作为通路继续扩展网络（源码 `classifyLocation` 把二者归为 `TERMINUS`）。
5. **网络上限**：`config.yml` 的 `networks.max-size` 默认 **200** —— 这是**在寻找联通网络时应用的限制**，官方说明"200 对玩家来说是非常慷慨的数字"。

#### 常见痛点

| 痛点 | 具体表现 | 来源 |
|---|---|---|
| **"电送不到"** | 缺少能源调节器 / 电容距离超限 / 把用电机当通路串联。全息只显示 "No Energy Network found" 或净亏，不给具体原因 | [能源与电力](https://slimefun-wiki.guizhanss.cn/Electric-Machines/) |
| **机器缓存不跨 tick 保留** | 机器自身缓存（非电容）在该 tick 未被使用就**被重置**，导致"电明明够但机器还是慢" | [能源与电力](https://slimefun-wiki.guizhanss.cn/Electric-Machines/) |
| **大机器抢电** | `storeRemainingEnergy` 按**遍历顺序**分配剩余电量，没有优先级/配额机制，先遍历到的用电机先吃饱 | 源码核实 |
| **tick 频率与产能感的错配** | 默认每 10 game tick 才结算一次，玩家看到机器"一顿一顿"地跑 | 源码核实 + [服务器优化指南](https://slimefun-wiki.guizhanss.cn/Server-Optimizations/) |
| **中期产能过剩** | 一台核反应堆 500 J/s 就能带满绝大多数用电机（最高耗电 180 J/s），后期电网**失去经营意义** | 源码核实 |
| **单位混乱** | 源码值是"每网络 tick"，tooltip 是 ×2 的 J/s，Wiki 标成 J/t ——三方不一致 | 源码核实 |
| **网络规模与性能正相关** | 官方建议把 `max-size` 从 200 调低、把 `cargo-ticker-delay` 从 0 调到 1 | [服务器优化指南](https://slimefun-wiki.guizhanss.cn/Server-Optimizations/) |

### 7.3 「基因 / 育种」方向的空白分析

**已存在的尝试**：
1. `GeneticChickengineering-Reborn` —— 唯一真正的"基因突变"附属，**但只覆盖鸡**，且已于 2026 年归档。
2. `GeneticManipulation` —— 有 DNA 物品概念，但停留在 RC-27 时代（MC 1.14–1.17）。
3. `Cultivation` —— 作物有 10/10/10 属性与交叉培育，是**最成熟的"植物育种"实现**，但已停更且要求 MC 1.19.4+ 的 display entity。
4. `Netheopoiesis` —— 65 种种子 + 隔格杂交，机制有趣但绑定"下界改造"主题。

**空白点（可差异化切入）**：

| 空白 | 说明 |
|---|---|
| **通用动物基因系统** | 没有任何附属把"基因"做成一等公民覆盖**所有**可繁殖动物（牛/羊/猪/鸡/兔/马/猫/狼/羊驼/蜜蜂…）。现有实现只覆盖鸡。 |
| **显隐性 / 等位基因模型** | 现有实现的"育种"基本都是**数值累加（10/10/10）**，没有孟德尔式的显隐性、纯合/杂合、基因型 vs 表现型区分。 |
| **跨物种 / 基因编辑** | 没有"提取基因 → 编辑 → 植入"的完整链路，也没有跨物种性状移植。 |
| **基因与机器自动化结合** | GeneticChickengineering 有"培育仓"，但没有把基因筛选接入 Busyfun 式的货运/能源网络做**大规模选育流水线**。 |
| **作物与动物基因统一体系** | Cultivation 管植物、GCE 管鸡，二者互不相通，没有统一的"遗传物质"抽象。 |
| **数据驱动的性状表** | 本体的 tag 文件（`crop_growth_accelerator_blocks.json`、`farmer_talisman_triggers.json` 等）已证明 Slimefun 的生态偏好数据驱动；但没有任何附属提供**可配置的性状/基因表**。 |

> **对 `HigherRedStoneFun` 的直接启示**：本项目已有的 `ItemGroup.GENETICS("基因工程", "<green>作物与动物的遗传改造")` 分类，**恰好落在这个真实空白上**。生态中没有活跃的竞品，且已有的三款尝试（GCE 已归档、GeneticManipulation 上古、Cultivation 停更且限 MC 1.19.4+）都不构成威胁。

### 8.4 对设计者的"负面需求清单"

综合以上，一个想改进 Slimefun 的项目，**优先要解决的是**：

1. **能源网络必须是增量的**（脏标记 + 拓扑缓存），不能每 tick 全量重算。
2. **导线不应该占节点**（把导线与机器分开计数），否则导线越多调度越慢。
3. **配电要有优先级/配额**，不能"先遍历到的先吃饱"。
4. **机器缓存要跨 tick 保留**，符合玩家对"电池"的常识。
5. **研究/解锁要可批量、可跳过、可配置**，不要做成纯时间税。
6. **网络诊断要可行动**：明确指出"这里缺调节器""这 3 台机器在抢电"。
7. **单位必须在 UI / 文档 / 代码三处一致**（Slimefun 在这点上是反面教材）。
8. **不要做季节性隐藏内容**，或者至少让服主能强制常驻。
9. **方块数据不要用 YAML 存**，且要**惰性加载**而非全量读入内存（Slimefun 官方 ADR 自认的失败点）。
10. **电容/储能的容量档位不要出现 4096 倍的断崖**，档位应平滑。
11. **发电机接入多个网络时的行为必须显式定义**（Slimefun 曾出现"每个网络都拿全额电力"的缺陷）。
12. **插件必须可移除**：不要把方块状态与地图强耦合到"移除插件就得删世界"的程度。
13. **机器人/机器必须尊重其他插件的保护逻辑**，否则会催生"补丁插件"（SlimeGlue）这种生态怪象。
14. **不要给玩家一个需要"在纸上画通道"才能理解的物流抽象**。
