## 二、明确要避开的坑（本插件已重构）

### 1. 能源网络：一个网络只允许一个调节器

```java
// EnergyNet.java:149-153
if (!regulator.equals(b.getLocation())) {
    updateHologram(b, "&4Multiple Energy Regulators connected");
    Slimefun.getProfiler().closeEntry(...);
    return;   // 整个网络停止工作
}
```

**问题**：玩家多放一个调节器，整张电网直接停摆，且只用一个悬浮字提示。
**本插件做法**：取消调节器概念，任何机器都能作为网络起点（`EnergyManager.getOrCreate`）。

### 2. 能源分配：按 Map 遍历顺序，无优先级

```java
// EnergyNet.java:166-186
for (Map.Entry<Location, EnergyNetComponent> entry : consumers.entrySet()) {
    int availableSpace = capacity - charge;
    demand = NumberUtils.flowSafeAddition(demand, availableSpace);
    if (remainingEnergy > 0) {
        if (remainingEnergy > availableSpace) {
            component.setCharge(loc, capacity);   // 先遍历到的先吃饱
            remainingEnergy -= availableSpace;
        }
        ...
    }
}
```

**问题**：先被遍历到的机器抢光所有电，后遍历到的永远吃不饱。
**本插件做法**：`MachineInstance.demand()` 返回「缓冲区空余量」，用电机按需补满，且没活干时需求为 0（不空转偷电）。

### 3. 电容在无余量时被强制清零

```java
// EnergyNet.java:211-213
} else {
    component.setCharge(loc, 0);   // remainingEnergy <= 0 时，电容被设为 0
}
```

**问题**：当发电量不足时，电容会被直接置 0，而不是「放电给用电机」。
**本插件做法**：`EnergyNetwork.tick()` 里发电机产出先充电池，用电机再从电池 `discharge()` 取电，是真正的充放电模型。

### 4. 导线本身是网络节点

`EnergyNet` 把导线方块也纳入网络计算，且每个网络 tick 全量重算。
**问题**：导线越多，重算成本越高——这是社区「基地一大就卡」的主要来源。
**本插件做法**：导线只是 BFS 通道，不进入 `generators/consumers/storages` 列表；网络带脏标记，只在方块变化时重建。

### 5. 方块数据用 YAML 存储（官方自认的设计错误）

官方 ADR-0001（2023-11）原文承认：YAML "good for a config format but **not good for a data store**"，
会产生 large files that can get corrupted，而其改造计划 **Phase 2–6 全部 `Not started`**。

**本插件做法**：
- 机器存档按**区块分节**，单台机器损坏不污染整个文件。
- 物品栏用 `ItemStack.serializeAsBytes()` + Base64（而非 YAML 物品序列化），保证自定义 PDC 标记不丢失。
- 作物基因直接存**区块 PDC**（免费、无上限、随区块自动存盘）。

### 6. 调度周期不统一

```java
// TickerTask.java:71-76
this.tickRate = Slimefun.getCfg().getInt("URID.custom-ticker-delay");
scheduler.runTaskTimerAsynchronously(plugin, this, 100L, tickRate);
```

**问题**：能源生产是「每网络 tick」值（0.5s），但 tooltip 显示 `×2` 的 J/s，Wiki 又标成 "J/t"——**三方单位不一致**。
**本插件做法**：全部统一为 **J/t**（每 tick 焦耳），配置、lore、`/hrf energy` 输出使用同一单位。

## 三、数值对照（用于平衡参考）

| 项目 | Slimefun4 | 本插件 v0.1 |
| --- | --- | --- |
| 单位 | J/s（源码为每 0.5s 值 ×2） | J/t |
| 发电机产能区间 | 8 – 1024 J/s | 8 – 400 J/t |
| 用电机耗电区间 | 2 – 180 J/s | 3 – 120 J/t |
| 机器 tick 频率 | 全网络统一 `custom-ticker-delay` | 每台机器可声明 `period(N)` |
| 机器数量 | 512 次注册 | 24 台 |
| 物品数量 | 534 个常量 | 88 个 |
| 研究解锁成本 | 258 个研究，合计 5431 XP 等级 | **无研究系统**（改为材料门槛） |

**关于产能过剩**：Slimefun 一台核反应堆（500 J/s）就能带动多数产线，
导致后期电网失去经营意义。本插件刻意压缩了区间（8–400 J/t），
并把核反应堆做成**有熔毁风险**的机器，让「电力」保持张力。

## 四、扩展点写法对照

### 写一台自定义用电机

```java
// Slimefun 的写法：继承 + 重写
public class MyMachine extends SimpleSlimefunItem<BlockTicker> {
    @Override
    public BlockTicker getItemHandler() {
        return new BlockTicker() {
            @Override
            public void tick(Block b, SlimefunItem item, Config data) { ... }
            @Override
            public boolean isSynchronized() { return true; }
        };
    }
}
```

```java
// 本插件的写法：注册定义 + 复用逻辑，不写新类
MachineRegistry.get().register(
    MachineDefinition.builder("my_machine", "我的机器", ItemGroup.POWER_MACHINES, Material.FURNACE)
        .recipeType(RecipeType.ELECTRIC_SMELTING)
        .energyRole(EnergyNode.Role.CONSUMER)
        .buffer(12_000L)
        .logic(RecipeMachineLogic.electric(6L))   // 直接复用
        .build());
```

**差异**：新增同类机器从「写一个类」变成「写一份注册」，这是本插件最核心的架构收益。

## 五、本插件的自检机制（Slimefun 没有的）

`/hrf selftest` 会验证 7 组核心机制共 61 项断言，包括：

- 物品 PDC 身份与 NBT 序列化往返
- 配方匹配与「只消耗所需数量」（防丢物品）
- 能源网络连通性、发电入电池、缓冲上限
- 机器完整加工生命周期
- **机器存档往返**（含自定义物品身份是否挺过序列化）
- 基因序列化、拼接取优、遗传合法性、区块 PDC 存取
- 作物/动物映射完整性

这对服主排障很有价值：能明确区分「插件坏了」和「玩家没接电线」。
