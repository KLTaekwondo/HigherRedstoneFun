# HigherRedStoneFun 玩法升级与优化设计（v0.1 设计说明）

> 本文是 v0.1 的**设计依据文档**。
> 它回答三个问题：粘液科技哪里做得好、哪里有问题、本插件如何做得更好。
> 配套文档：`01-粘液科技玩法调研与核心统计.md`（调研与统计）、`02-Slimefun4源码架构分析.md`（源码分析）。

---

## 1. 设计立场

我们不做「粘液科技的复刻」，而是**保留它验证过的乐趣内核，替换掉它被证明有问题的部分**。

调研文档（结论 1–10）给出了可核实的证据基础。下面每一条优化都对应一个具体的、有出处的痛点。

| 粘液科技的乐趣内核（保留） | 粘液科技的痛点（替换） |
| --- | --- |
| 图鉴驱动的科技树探索感 | 258 个研究、合计 5431 XP 等级的时间税 |
| 「把机器摆出来看它工作」的满足感 | 能源网络要求「有且仅有一个调节器」，配置脆弱 |
| 从手工到全自动的成长曲线 | 中期产能过剩（发电机 8–1024 J/s vs 用电机 2–180 J/s） |
| 附属插件生态带来的玩法纵深 | BlockStorage 用 YAML 存方块数据（官方 ADR 自认错误设计） |
| 多方块工作台的仪式感 | 导线本身就是网络节点，规模一大就卡 |

---

## 2. 六项核心优化

### 优化一：能源网络 —— 导线不再占用节点

**问题（调研结论 6）**

粘液科技的 `EnergyNet` 把导线方块也纳入网络计算，并且**每个网络 tick 全量重算**而非增量更新。导线越多，重算成本越高。社区里「基地一大就卡」的抱怨主要来自这里。

此外它还有一个硬约束：**一个网络必须有且只有一个能源调节器**，多放一个就整个网络停止工作。这是纯粹的配置陷阱。

**我们的做法**

见 `energy/EnergyNetwork.java`：

1. **导线不是节点**。`EnergyNetwork.rebuild()` 的 BFS 只把真正的机器登记进 `generators / consumers / storages` 三个列表；导线仅作为遍历通道。因此放一万根导线，调度开销不变。
2. **拓扑缓存 + 脏标记**。网络只在方块变化时重建（`markDirty()` → 下次 tick 重建）。稳态下每 tick 是 O(机器数) 的简单算术，而不是 O(全网方块数) 的图遍历。
3. **BFS 有硬上限**（`MAX_SCAN_BLOCKS = 4096`，`MAX_MACHINES = 512`）。超大基地不会让单个 tick 无限变长，这在原版是缺失的保护。
4. **取消调节器依赖**。任意机器都能作为网络的起点，不存在「多放一个就全停」的陷阱。
5. **网络合并自动处理**。用导线连通两个网络时，旧网络被 `dissolve()` 吸收，不会出现同一批机器被两个网络重复 tick 的问题。

**玩家可见的变化**

- 导线用常见方块（铜块 / 避雷针 / 末地烛），摆多少都行。
- 不需要「能源调节器」作为必需件——它在本插件里只是一个**大容量储能设备**，可选。

### 优化二：能源分配 —— 按缓冲区补电，而不是按遍历顺序抢

**问题（调研结论 6）**

粘液科技的 `storeRemainingEnergy` **按遍历顺序**分配电量，没有优先级。结果是：先被遍历到的大机器可能抢光所有电，小机器永远吃不饱。而且机器自身的缓存**不跨 tick 保留**（官方 Wiki 明确说明会被重置）。

**我们的做法**

见 `energy/EnergyNode.java` 与 `machines/MachineInstance.java`：

1. **缓冲区补满模型**。机器只在「确实有活要干」时才把 `requestPower` 置位，需求量 = `bufferCapacity - energyStored`。没活干的机器需求为 0，**不空转偷电**。
2. **电池优先**。发电机产出的电先充入所有电池，充满后的余量才直供用电机。这符合玩家的直觉（「先存起来」）。
3. **电池均衡**（`balanceStorages()`）。把高于平均值的电池的多余电量转移给低于平均值的，避免「一块满一块空」的假性缺电。
4. **解耦 tick 顺序**。因为需求是「补满缓冲区」，机器调度与能源调度的先后顺序不影响结果，消除了原版里微妙的时序耦合。

### 优化三：机器实现 —— 定义 / 状态 / 逻辑三分

**问题（调研结论 3）**

粘液科技的机器是深继承层级：每种机器往往对应一个新类。生态里大量附属插件的代码是「复制一份差不多的类改两行」，导致重复逻辑与不一致的 bug。

官方 ADR-0001（2023-11）承认 `BlockStorage` 用 YAML 存方块数据是错误设计（"good for a config format but **not good for a data store**"），会产生 large files that can get corrupted——而其改造计划 **Phase 2–6 全部 `Not started`**。

**我们的做法**

拆成三个正交的部分：

| 部分 | 类 | 职责 |
| --- | --- | --- |
| 定义（不可变） | `MachineDefinition` | 界面布局、能源角色、产能、周期、lore |
| 状态（可持久化） | `MachineInstance` | 物品栏、进度、燃料、储能、计数 |
| 逻辑（可复用） | `MachineLogic` | tick 行为、发电/耗电 |

收益：

- **新增一台同类机器 = 注册一份定义 + 一条配方，不写新类。**
  v0.1 的 6 台基础机器全部复用同一个 `RecipeMachineLogic`。
- **`MachineLogic` 是接口而非抽象类**，燃料机器与电力机器共用同一份 `RecipeMachineLogic`，只靠构造参数区分。
- **存储按区块分节**，单台机器出问题不会污染整个存档；序列化用 `ItemStack.serializeAsBytes()` + Base64（而不是 YAML 的物品序列化），保证自定义 PDC 标记不丢失。

### 优化四：机器调度 —— 遍历「区块」而不是遍历「机器」

**问题**

无论原版还是常见附属，机器 tick 通常是「遍历所有机器，检查是否加载」。当存档里有十万台机器时，这个循环本身就有成本。

**我们的做法**

见 `machines/MachineManager.java`：

- 机器按**区块**分桶存放（`Map<Long, List<MachineInstance>>`）。
- tick 时遍历的是**包含机器的区块**，用区块内第一台机器判断加载状态，未加载则整块跳过。
- 开销只与「当前加载的、含机器的区块数」相关，**与存档里的机器总数解耦**。
- 每台机器可声明 `period(N)`，被 `tickCounter % N` 节流（例如工作台不需要每 tick 检查）。

另外：**单台机器抛异常不会中断其它机器**（try/catch 隔离 + 日志记录），这是原版容易「一台机器写错卡死整个 tick」的问题。

---

### 优化五：物品身份 —— 用 PDC 单键，而不是显示名或第三方 NBT 库

**问题**

依赖显示名做物品识别会被铁砧重命名破坏；依赖第三方 NBT-API 库会增加部署复杂度与版本兼容风险。

**我们的做法**

见 `items/ItemRegistry.java`：

- 所有自定义物品用 **一个 `NamespacedKey` 字符串**标记在 `PersistentDataContainer` 上。
- `sameItem()` 对自定义物品**只比较 ID**，对原版物品才退回 `isSimilar()`。
- `normalize()` 可以把玩家放进机器的物品「洗干净」（剥离附魔、自定义名），防止把附魔钻石当普通钻石用掉。
- 方块身份用**坐标 + 材质**双重校验（该 API 版本已移除方块级 PDC），与粘液科技的 `BlockStorage` 思路一致，但多了材质校验来防「方块被替换后幽灵机器还在跑」。

---

### 优化六：不再强制研究解锁

**问题（调研结论 1）**

粘液科技有 258 个研究、合计 **5431 个经验等级**的成本。对单人玩家这是漫长的前期时间税，且「不知道该研究什么」是常见的流失点。

**我们的做法**

- 图鉴**默认全部可见**，玩家可以自由规划科技树，而不是被经验等级卡住。
- 门槛改为**材料门槛**：想造电力机器，先去矿里挖铜做导线、做电路板，而不是去刷经验。
- 这保留了「目标感」，去掉了「纯等待」。

## 3. 玩法升级：基因工程模块

### 3.1 为什么选这个方向

这是**经调研核实的真实空白**（调研结论 9）：

- 本体（Slimefun4）的农业能力只有三类生长加速器，**没有任何遗传机制**。
- 生态中沾边的只有三款，且全部出局：
  - `GeneticChickengineering-Reborn` —— **已归档**，且只覆盖鸡。
  - `GeneticManipulation` —— RC-27 时代的上古项目。
  - `Cultivation` —— 最接近（交叉培育 + 10/10/10 属性），但**已停更**且硬性要求 MC 1.19.4+。
- 空白点包括：**通用动物基因系统、显隐性模型、基因编辑链路、基因+自动化流水线、作物与动物的统一遗传抽象**。

### 3.2 核心设计：可遗传的四基因位系统

见 `genetics/Genome.java`：

| 基因位 | 效果 | 满级收益 |
| --- | --- | --- |
| **生长** | 作物成熟更快、幼崽更快成年 | 约 3 倍速 |
| **产量** | 收获数量与掉落物更多 | 约 3.5 倍量 |
| **抗逆** | 抵抗踩踏；满级完全免疫 | 免踩踏 |
| **活力** | 自动补种、繁殖加成 | 100% 自留种 |

每个基因位 **0–5 级**，共 20 点总强度。

**收益曲线刻意做成递减**（`1 + 0.2L + 0.04L²`）：越接近满级越难，避免「一步到位」让玩法过早结束。

### 3.3 五步循环 —— 让「培育」成为真正的玩法

```
采集 ──→ 测序 ──→ 拼接 ──→ 注入 ──→ 收获
 │        │        │        │        │
 │        │        │        │        └─ 种植/孵化，基因随作物与动物保存
 │        │        │        └─ 基因组 → 改良种子 / 胚胎
 │        │        └─ 两个基因组逐位取优 + 概率突变（核心循环）
 │        └─ 样本 + 引物 → 基因组（4 个基因位）
 └─ 潜行 + 空样本瓶 右键 成熟作物 / 家畜
```

**关键设计：拼接是核心，不是随机刷。**

- `splice(a, b)`：每个基因位**独立取双方较大值**，并有概率 **+1 突变**。
- 因此玩家可以「把 A 的高生长和 B 的高产量合到一起」——这是**定向育种**，而不是抽卡。
- 机器等级决定突变率：`基因拼接机` 12%，`基因拼接机 MK-II` 30%。**升级机器本身有明确收益。**

**关键设计：动物基因可遗传。**

- `inherit(parentA, parentB)`：子代每个基因位随机来自父方或母方，另有 10% 概率 +1、5% 概率 −1。
- 于是「一代代选育出高产牛群」成为可能——这是原版生态完全没有的体验。

### 3.4 存储方案 —— 作物基因存在区块 PDC

该 API 版本已移除方块级 `PersistentDataContainer`（`CustomBlockData` 不存在）。

我们选择**区块的 PDC**（`Chunk implements PersistentDataHolder`）来存作物基因：

- **免费且无上限**：不需要为每种作物维护一个 `BlockStorage`（这正是粘液科技 YAML 存储出问题的根源）。
- **随区块自动存盘与卸载**，不需要额外的保存逻辑。
- 键名 `hrf_crop_<x>_<y>_<z>`，读取是 O(1)。

动物基因存在**实体 PDC** 上，随实体保存，天然跟随动物移动。

### 3.5 经济闭环

基因培育舱（`GrowthChamberLogic`）是经济出口：

- 产出与基因直接挂钩：**生长**决定耗时、**产量**决定数量、**活力**决定是否消耗种子。
- 一条完美基因产线相比野生种子有**数倍效率差距**。
- 而达成完美基因需要多代拼接 —— 投入（电力 + 时间）与回报（效率）形成正反馈。

## 4. 三个模块的科技树

```
                 ┌─────────────────────────────────────┐
                 │  增强工作台（手工，无需燃料）          │
                 └──────────────┬──────────────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
   ┌─────────┐            ┌──────────┐            ┌──────────┐
   │ 基础机器 │            │ 电源线   │            │ 基因线   │
   │ 研磨机   │            │ 燃煤发电 │            │ 采样器   │
   │ 压制机   │            │ 太阳能   │            │ 测序仪   │
   │ 冶炼炉   │──零件─────→│ 地热     │──精密件──→│ 拼接机   │
   │ 离心机   │            │ 电容     │            │ 注入器   │
   │ 锯木机   │            │ 核反应堆 │            │ 培育舱   │
   └─────────┘            └──────────┘            └──────────┘
        │                       │                       │
        └───────────────────────┴───────────────────────┘
                                │
                       组装机 / 分子重组机
                       （终局合成：核反应堆、MK-II 设备）
```

- **基础机器**无需电力，是所有人的起点。
- **电力机器**需要基础机器产出的零件（铜导线 → 电路板 → 高级电路板）。
- **基因机器**需要电力机器的精密件（高级电路板、强化框架）——所以基因是**后期内容**，有清晰的前置。

## 5. v0.1 的已知取舍与 v0.2 计划

诚实记录 v0.1 没做的事：

| 项目 | v0.1 状态 | v0.2 计划 |
| --- | --- | --- |
| 物流（管道 / 货运） | **未实现**，需要手动搬运 | 仿照 CargoNet 做管道与节点 |
| 配方配置化 | 硬编码在 `Recipes.java` | 迁移到 YAML，支持数据包式扩展 |
| 存储性能 | 每世界一个 YAML，按区块分节 | 改为按区块分文件，避免单文件膨胀 |
| 区块加载恢复 | 每次读整个 YAML 再筛区块 | 分文件后按需读单区块 |
| 附属 API | 无 | 开放 `MachineLogic` 注册入口给第三方 |
| 基因位 | 4 个（生长/产量/抗逆/活力） | 计划加入显隐性（等位基因）模型 |
| 蜜蜂 / 特殊生物 | 仅有胚胎与采样 | 补充产物加成 |
